# Neural networks: Learning a function

<Byline readingTime={metadata.readingTime} />


In 1989, researchers at Bell Labs built a system to read handwritten ZIP codes off envelopes. The dataset they eventually assembled (70,000 grayscale images of handwritten digits, called [MNIST](https://en.wikipedia.org/wiki/MNIST_database)) became machine learning's "hello world," and it's where we start too. (60,000 of the images are used for training; 10,000 are held back, for a reason that closes the chapter.)

<span className="mt-2 block text-center text-sm text-gray-500 dark:text-gray-400">Samples from MNIST. Image by [Josef Steppan](https://commons.wikimedia.org/wiki/File:MnistExamples.png), CC BY-SA 4.0.</span>

## Where rules fail, examples work

Programming a computer to read these scribbles is brutally hard with classical logic. There are no hard-and-fast rules for what makes a 5 a 5 (every rule you write has a thousand exceptions), and early rule-based vision systems fell on their faces. The same wall appears wherever the input is fuzzy: parsing an English sentence, recognizing a face in a photo. This is why these problems stayed unsolved for decades while computers conquered chess. But problems like these have a saving grace: the rules are hard to write, but *examples* are cheap — and the discipline for extracting patterns from examples is statistics.

That's the thread this chapter pulls on:

1. We treat digit-reading as a statistics problem. The simplest statistical tool is a regression (give every pixel a weight, add up the evidence), and this alone reads 92% of digits correctly.
2. But a regression is linear: every pixel votes independently, so it can't express *interactions*, where one stroke's meaning depends on another. Stacking regressions with small decisions between them (a neural network) can approximate far richer functions.
3. "Learning" means *incrementally improving* the weights from feedback — a random search wouldn't qualify. Gradient descent supplies the increments (measure how wrong the current weights are and follow the slope downhill), and the chain rule (backpropagation) makes that slope cheap to compute, even for millions of weights.

A loose but useful analogy to programming: pick a *family* of functions (an architecture with millions of tunable parameters — the signature), define "good output" (a loss function — the spec), and let an optimization algorithm find the family member that fits the examples. Nothing "programs itself": the network is a fixed, highly parameterized function, and what gets learned are its parameters.

A model's life has two distinct phases. **Training** is when the optimization algorithm is improving the weights — the model is being fit. **Inference** is everything after: the weights are frozen, and the model is simply being *used*, like any other function. This chapter is almost entirely about training; by the end of the book, inference will have earned three chapters of its own.

## The model: from a matrix to an MLP

Back to MNIST — an MNIST image is 28×28 pixels. Flatten it and you get a vector $x$ of 784 numbers between 0 (white) and 1 (black). We want a function that maps that vector to an answer: which digit is this?

<FlattenFigure />

The problem itself isn't deterministic. A sloppily written 5 shades into a 2; even humans disagree about the worst examples. So a function that returns *the* answer is the wrong shape — what we want is a function that weighs the evidence and returns a *score* for each of the 10 candidates, soon converted into probabilities. Again: statistics, not logic.

Statistics' simplest mechanism for turning weighted evidence into a score is a regression — a linear function of the input:

$$
\tip{10 scores — one per digit}{y} = \tip{a 10×784 matrix of learned weights}{W}\tip{the image as a vector of 784 pixel values}{x} + \tip{10 learned offsets — one per digit}{b}
$$

where $W$ is a 10×784 grid of weights (a **matrix**) and $b$ holds ten learned offsets (the **biases**), letting each digit's score start high or low before any pixel votes. Each row of $W$ is effectively a template: the dot product between the input and that row measures "how much does this image look like this row's digit." This alone (a *linear classifier*) gets about 92% accuracy on MNIST: a matrix multiply is already a primitive form of pattern matching.

<LinearScoresFigure />

Why does a linear model top out at 92%? Because of what linearity *means*: each pixel gets one fixed weight, votes independently, and the votes are simply added up. A weighted sum is a linear combination — pixels do combine, but only *additively*. What it can't express is an **interaction**: "this pixel is evidence for an 8 *only if* this other region is dark too." The pixels of a 5 and a 2 overlap heavily; what separates them is strokes appearing *together*, a conjunction independent adding can't reproduce. In programming terms: a linear function is a program with no `if` statements — one pass of weighted arithmetic, no decisions that depend on the input.

Stacking two linear layers doesn't help: composing linear functions gives another linear function ($W_2(W_1x) = (W_2W_1)x$ — the composition collapses into one matrix). However many layers you stack, you've written a longer program with still no `if` statements.

The fix is to insert a nonlinearity between the layers, and the field has settled on the almost comically simple [ReLU](https://en.wikipedia.org/wiki/Rectifier_%28neural_networks%29) (rectified linear unit): $\mathrm{relu}(x) = \max(0, x)$, applied to each **unit** (or *neuron*) — one weighted sum in a layer's output. Below zero the unit outputs nothing; above zero it passes its signal through — a branch, the smallest possible `if`:

<ReluFigure />

With a nonlinearity between them, the layers stop collapsing: the first layer computes features, the ReLU *decides* which are present, and the second layer weighs those decisions together.

Stack linear layers with nonlinearities between them and you have a **multi-layer perceptron** (MLP):

$$
y = \tip{second layer: weighs combinations of features into digit scores}{W_2} \, \tip{the branch: zeroes out features that aren't present}{\mathrm{relu}}(\tip{first layer: detects 512 features in the pixels}{W_1 x + b_1}) + b_2
$$

With one **hidden layer** (the middle layer, neither input nor output) of 512 units (a designer's choice, not a derived number), this gets ~98% on MNIST. Intuitively, the first layer learns to detect features (strokes, loops, corners), and the second layer learns to combine features into digits.

<MlpFigure />

But the stack exacts a price. A lone regression can be *solved*: for a linear model, calculus hands you the best-fit weights directly — set the derivative of the error to zero and solve (least squares, the machinery that fits a spreadsheet's trend line). The moment a nonlinearity sits between two matrices, that machinery dies. For a linear model the error surface is a smooth bowl — "set the derivative to zero" is a system of *linear* equations with one solution. Add the ReLUs and the surface shatters: each unit is either on or off for a given input, so $n$ units carve the surface into up to $2^n$ regions with a different linear rule inside each — and "set the derivative to zero" becomes a system of nonlinear equations nobody can solve in general. This isn't just empirical pessimism: [Blum and Rivest proved](https://people.csail.mit.edu/rivest/pubs/BR93.pdf) that optimally training even a three-neuron network is NP-complete, so a general-purpose *efficient* recipe for the best $W_1$ and $W_2$ would, among other things, resolve P vs. NP. The best anyone knows how to do is start with random weights and improve them *iteratively* — which is exactly what the rest of this chapter is about.

## The learning: gradient descent

So here's where we are: an MLP with ~400,000 weights (784×512 + 512×10 + biases = 407,050), every one initialized to a random number. Feed it a handwritten 7 (the one from the figures above — our running example) and it reports roughly 10% on every digit. Of course it does; it's random. How do we get 400,000 random numbers to take on *useful* values?

Since we can't solve for them, we iterate: nudge the weights, check whether the model got better, keep the nudges that help, repeat a few hundred thousand times. For now, assume that "did the model get better?" is a single number we can compute — a score, called the **loss** $L$, that measures how wrong the model is on the training data, where lower is better. (Constructing it carefully is the next section's job; here we only need that it exists and is smooth.)

Here's the situation for any single weight. Somewhere out there is its *optimal* value; the closed-form door to finding it slammed shut a section ago. What we *can* compute, at whatever value we currently hold, is how bad it is (the loss) and, because the loss is smooth, which direction makes it worse (the derivative). So, humbly: repeatedly move in whichever direction makes things less bad, and stop when no direction helps. You may never learn where the best value was, but you'll settle somewhere *least bad*.

<GradientDescentFigure />

Scaled up to all 400,000 weights at once, this is **gradient descent**: compute the gradient of the loss (the direction that increases it fastest) and take a small step the other way.

$$
\tip{a weight}{\theta} \leftarrow \theta - \tip{the learning rate: how big a step to take}{\eta} \tip{the slope: how much the loss changes as this weight changes}{\frac{\partial L}{\partial \theta}}
$$

This update runs for every weight simultaneously. Each weight's partial derivative, collected into one big vector, is the **gradient** — papers write the whole update as $\theta \leftarrow \theta - \eta \nabla_\theta L$, and now you can read that too.

Why a *small* step — and why must the steps shrink as we close in? Take the same confident stride every time and you'd overshoot the valley floor, land on the opposite slope, and overshoot again — orbiting the minimum forever. Gradient descent has an elegant built-in fix: the step is $\eta$ *times the slope*, and the slope fades to zero at the minimum, so the steps shrink automatically as you arrive — exactly what the animation above shows. Here's the fixed-stride version for comparison:

<FixedStepFigure />

The multiplier $\eta$ is the **learning rate**, deep learning's most famously finicky number. (Adaptive optimizers like Adam, a few pages on, blunt the worst of it — but they still take a learning rate, and the sweep below remains standard.) Too small is merely slow — thousands of timid steps down a hill you could have descended in ten. Too large is fatal, in a way that seems to contradict the self-shrinking steps we just celebrated. That guarantee had a hidden assumption: that each step lands you *closer* to the minimum, where the slope is gentler and the next step therefore smaller. Overshoot far enough, though, and you land on the far slope at a point *steeper* than the one you left. Now "step proportional to slope" works against you: a steeper landing means a bigger next step, which means a steeper landing still. The same feedback loop that damped the walk now amplifies it, and the parameters ricochet outward until the numbers overflow.

On a one-weight toy (loss $a\theta^2$, the bowl from the figures above) you can make this exact: the slope of $a\theta^2$ is $2a\theta$, so one update moves $\theta$ to $\theta - \eta \cdot 2a\theta = (1 - 2a\eta)\,\theta$ — every step multiplies your distance from the minimum by $|1 - 2a\eta|$. Keep $\eta$ below $1/a$ and that factor is less than one: the walk converges. Above it, every step lands further out than it started.

Two practical modifications every framework makes:

- **Stochastic** gradient descent (**SGD**, the name you'll see in every framework and paper): you *could* compute the exact gradient over all 60,000 images before each step. But consider what that buys you. The gradient from a random sample of images is an *unbiased* estimate of the full gradient (right on average, noisy per sample), and averaging $n$ samples shrinks the noise only like $1/\sqrt{n}$ (statistics' standard-error rule) while the cost grows linearly with $n$. Worse, extra precision is mostly thrown away: you only take one small step in that direction, and after the step the landscape has changed and the direction must be recomputed anyway. So instead, estimate the gradient on a random **batch** (say, 128 images) per step: for the price of one perfect step you take ~500 noisy ones (60,000 ÷ 128 ≈ 470 batches per pass, call it 500), and 500 stumbles downhill travel much farther than one flawless stride. (The noise even turns out to *help* — it jiggles the trajectory out of flat regions and bad ruts.)
- **Epochs**: one full pass through the training data is an epoch. Small datasets get looped over many times. (Foreshadowing: LLMs, trained on trillions of tokens, typically see their data roughly *once* — more on that in Chapter 7.)

## The loss: measuring wrongness

Now let's construct the number we've been assuming. Gradient descent quietly imposed two requirements on it: the loss must be *differentiable* (we take its gradient), and it should change *continuously* as the model improves (a compass that only moves in rare jumps gives the search no direction). The loss is, literally, the spec the model will be optimized against.

Those requirements immediately disqualify the obvious candidate: accuracy, percent correct. Nudge one weight slightly and usually *no* prediction flips, so accuracy doesn't move at all — flat almost everywhere, gradient zero, no signal. What we want instead is a number that rewards moving from "99% sure it's a 3" to "60% sure it's a 3" on an image of a 5, even though both are, discretely, the same mistake. That means grading the model's *confidence*, not just its verdict — and for that, its outputs need to be probabilities.

The 10 output scores (called **logits**) are unbounded real numbers. To interpret them as a probability distribution, we pass them through **softmax**:

$$
\tip{the probability assigned to digit i}{p_i} = \frac{\tip{exponentiate: always positive and amplifies gaps}{e^{y_i}}}{\tip{normalize: divide by the total so everything sums to 1}{\sum_j e^{y_j}}}
$$

Softmax exponentiates each score (positive, with differences amplified) and normalizes to a sum of 1 — here applied to the linear classifier's scores for the 7:

<SoftmaxFigure />

The target it's graded against is the label written as a **one-hot** vector — all zeros except a 1 on the correct digit: a probability distribution with all of its mass on the truth. The grading rule is **cross-entropy loss**: the negative log (the *natural* log, base $e$; deep learning's logs all are, unless marked) of the probability the model assigned to the correct answer.

$$
\tip{the loss — what gradient descent minimizes}{L} = \tip{negated so that more confidence means less loss}{-\log}(\tip{the probability the model gave the right answer}{p_{\text{correct}}})
$$

The log of a probability has a name you'll meet in every LLM API: a **logprob**. Probabilities live in [0, 1], so logprobs live in [−∞, 0] (zero when the model is certain, increasingly negative as it's surprised), and cross-entropy is just the correct answer's logprob, negated. If the model puts probability 1 on the right answer, the loss is 0. If it puts probability 0.01 on it, the loss is $-\ln(0.01) \approx 4.6$.

<details>
<summary>Why the log, rather than something simpler like penalizing $1 - p_{\text{correct}}$?</summary>

One statistical reason and one practical one. Statistically, the natural goal is to maximize the probability of getting the *whole training set* right — and since that's a product of 60,000 per-example probabilities, it's hopeless to work with directly (it would underflow any floating-point format, and calculus hates products). Taking the log turns the product into a *sum* of per-example terms — exactly our loss — without changing what's being maximized.

Practically, the log changes how wrongness is punished: a linear penalty barely distinguishes "wrong at 1%" from "wrong at 0.001%", so the gradient fades just when correction is most needed. Under the log, every additional order of magnitude of overconfident wrongness costs the same again — the loss stays fierce precisely where the model is most confidently wrong.

(There's a third, deeper reading — the logprob, taken in base 2, is the number of bits needed to encode the right answer under the model's beliefs; log bases differ only by a constant factor, so switching never changes what's being minimized — and it pays off next chapter, when training a language model turns out to be compression.)

</details>

Averaged over the dataset, this single number summarizes how wrong the model is — smooth, differentiable, and falling steadily as confidence shifts toward the right answers. "Learn to read digits" has become "minimize this function."

## Backpropagation: the chain rule, industrialized

How do you compute a gradient with respect to a million parameters? Running the network front-to-back (pixels in, through the layers, predictions out) is called a **forward pass**; it's what the model does every time it makes a prediction (during training, we then score those predictions against the label to get the loss).

The naive recipe: nudge one weight by a tiny $\varepsilon$, re-run the network, and read off the loss change — a derivative estimate costing one forward pass *per weight*, 400,000 of them per training step. [Backpropagation](https://karpathy.medium.com/yes-you-should-understand-backprop-e2f06eab496b) computes *all* of the gradients (exactly, not by nudging) in about the cost of two forward passes. The engine is the **chain rule** from calculus. As a reminder: when functions are composed, their rates of change multiply. Take the simplest case from our own network — the loss $L$ depends on the prediction $y$, and the prediction depends on some weight $w$. Then:

$$
\frac{\partial L}{\partial w} = \tip{how much the loss moves when y moves}{\frac{\partial L}{\partial y}} \cdot \tip{how much y moves when the weight moves}{\frac{\partial y}{\partial w}}
$$

Nudge the weight: its effect on the prediction is scaled by $\partial y/\partial w$, and that effect on the loss is scaled again by $\partial L/\partial y$ — two links in a chain, two factors in a product. A deep network is just a longer chain.

Backprop computes every weight's derivative (exactly, not by estimate) in one sweep:

1. **One forward pass**, keeping every intermediate value in memory instead of discarding it — the first layer's weighted sums $h$, the ReLU'd versions $a$, the prediction $y$, the loss $L$. These intermediate values (everything computed between input and output, as opposed to the weights computed *with*) are called **activations**; the term recurs all book.
2. **One backward sweep.** Start at the loss and walk the network back to front. At each value, compute "how much does the loss change if *this* changes" — which is cheap, because it's just the answer already computed for the value *after* it, times one local derivative. And the local derivatives are known analytically: every operation in the network is simple (multiply, add, relu, softmax), and calculus gives each one's derivative as a formula — evaluated instantly using the values remembered from the forward pass. No $\varepsilon$ anywhere.
3. **Collect the gradients along the way.** Every time the sweep passes a weight, that weight's exact $\partial L/\partial w$ falls out as a byproduct. By the time it reaches the input, you hold the derivative for *all* 400,000 weights — from one backward walk that costs about as much as the forward one.

Here is the whole thing running on a tiny two-layer network, with real numbers — four forward calculations, then four backward, one per step:

<BackpropFigure />

Watch what the backward pass reuses: $\partial L/\partial \hat{y}$ (the hat on $\hat{y}$ is the figure's way of marking "the model's estimate" — the prediction we've been calling $y$) is computed once and feeds every gradient below it; each $\partial L/\partial h$ is computed once and feeds every weight into that unit. That reuse is dynamic programming — compute each subresult once, use it everywhere — and it's how a million gradients cost about the same as two forward passes instead of a million.

Then gradient descent acts on all of them *simultaneously*: every weight takes its own step, scaled by its own partial derivative — $\theta \leftarrow \theta - \eta \, \partial L/\partial \theta$, applied to all 400,000 at once. One forward pass, one backward pass, one synchronized update: that is a **training step**, and a training run is millions of them.

In practice you never write this by hand. Frameworks like PyTorch record the **computational graph** as your code runs and derive the backward pass automatically (this is "autograd"). Here is the entire training loop, for real:

```python showLineNumbers
model = nn.Sequential(
    nn.Linear(784, 512),
    nn.ReLU(),
    nn.Linear(512, 10),
)
opt = torch.optim.SGD(model.parameters(), lr=0.1)

for images, labels in dataloader:          # batches of 128
    logits = model(images.view(-1, 784))   # forward pass
    loss = F.cross_entropy(logits, labels) # softmax + neg-log-likelihood
    opt.zero_grad()
    loss.backward()                        # backprop: fills in .grad
    opt.step()                             # gradient descent step
```

Every model in this book (up to and including the frontier ones) is trained by a scaled-up version of these ten lines.

## Better optimizers: momentum and Adam

Vanilla SGD works, but a real network's loss landscape is a mess of ravines and plateaus, and two refinements are so universal you should know them by name.

**Momentum** keeps a running average of recent gradients (exponentially decaying: recent steps weigh most) and steps in that direction — like a ball rolling downhill, it smooths over noise and powers through small bumps.

**[Adam](https://arxiv.org/abs/1412.6980)** additionally tracks a running average of the gradient's *magnitude* for each individual parameter, and scales each parameter's step size accordingly: parameters with consistently large gradients get smaller steps, and vice versa. It's a per-parameter adaptive learning rate. The variant actually used everywhere is [AdamW](https://arxiv.org/abs/1711.05101), which fixes how **weight decay** — a regularization term: a gentle pressure shrinking every weight toward zero each step, so large weights must be earned through the data (why that protects is the closing section) — interacts with the adaptivity (the details of that fix wait for Chapter 7, where the optimizer wars resume).

When you read an LLM paper and see "AdamW, β₁ = 0.9, β₂ = 0.95," those betas are just the decay rates of the two running averages. And file one fact for the infrastructure chapters: Adam stores two extra numbers *per parameter*, so the optimizer's state is twice the size of the model itself.

## Putting it together: learning XOR

Let's watch a complete training run — on a problem a linear model provably cannot solve. **XOR** ("exactly one of the two inputs is on") is the famous one: no threshold on any weighted sum of the two inputs can fire for (0,1) and (1,0) while staying silent for (0,0) and (1,1). (Proof: firing on the singles needs $w_1 \ge t$ and $w_2 \ge t$; silence on (1,1) needs $w_1 + w_2 < t$ — impossible for positive $t$. [Minsky and Papert's 1969 book](https://en.wikipedia.org/wiki/Perceptrons_%28book%29) made this limit famous and stalled the field for a decade.) Two hidden neurons and a ReLU handle it.

The network below is as small as they come — two inputs, two hidden units, one output squashed through a *sigmoid* (softmax's two-option sibling, turning the score into a probability between 0 and 1). It trains on all four cases of XOR at once, by plain gradient descent:

## Generalization: the point of all this

One last concept, because it's the difference between machine learning and curve fitting. A model with enough parameters can *memorize* its training set — and score 100% on it while being useless on new data. This is **overfitting**, and it's why we always hold out a **test set** the model never trains on, and report accuracy there. In practice you watch *two* loss curves during training — one on training data, one on held-out data — and the number you actually care about is the second. When the training curve keeps falling but the held-out curve turns back upward, the model has stopped learning and started memorizing.

Besides more data, the classic in-training countermeasures are **regularization** techniques:

- **Weight decay**, which you met inside AdamW.
- **Dropout**: during training, zero out a different random fraction of the activations each step, so no unit can rely on precise co-conspirators. (At inference, dropout is off.) For a decade it was in every architecture diagram; Chapter 7 holds a surprise about its fate in LLMs.

The entire game is generalization: we don't want a model that knows these 60,000 digits, we want one that has learned what digits *are*. That tension returns with a vengeance when we discuss benchmark contamination in Chapter 9.

One more thing: nothing in this chapter was actually about digits. The machinery was generic — vectors in, scores out, loss down — pointed at 28×28 images only because the labels came free, and labels are the scarce resource: someone had to write 70,000 of them. So carry this into the next chapter: the largest pile of labeled data our species has produced is *text*, where every word is automatically a label for the words before it. What happens if we point this machinery at that?
