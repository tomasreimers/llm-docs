# Neural networks: Functions that learn


In 1989, researchers at Bell Labs built a system to read handwritten ZIP codes off envelopes. The dataset they eventually assembled — 70,000 grayscale images of handwritten digits, called [MNIST](https://en.wikipedia.org/wiki/MNIST_database) — became the "hello world" of machine learning, and it's where we'll start too.

<Image src={MnistPng} alt="A grid of sample handwritten digits from the MNIST dataset, ten examples each of 0 through 9" />

<span className="mt-2 block text-center text-sm text-gray-500 dark:text-gray-400">Samples from MNIST. Image by [Josef Steppan](https://commons.wikimedia.org/wiki/File:MnistExamples.png), CC BY-SA 4.0.</span>

## Programming with data

Programming a computer to read these scribbles is brutally hard with classical logic. There are no hard-and-fast rules for what makes a 5 a 5 — every rule you write has a thousand exceptions — and the early vision systems built on hand-written rules fell on their faces. The same wall appears wherever the input is fuzzy: parsing an English sentence, recognizing a face in a photo. This is why these problems stayed unsolved for decades while computers conquered chess. But problems like these have a saving grace: the rules are hard to write, but *examples* are cheap — and the discipline for extracting patterns from examples is statistics.

That's the thread this chapter pulls on, in three steps:

1. We treat digit-reading as a statistics problem. The simplest statistical tool is a regression — give every pixel a weight, add up the evidence — and this alone reads 92% of digits correctly.
2. But a regression is linear: it can weigh each pixel, but it can't see *combinations* of strokes. Stacking regressions with small decisions between them — a neural network — lets us learn arbitrary functions, not just linear ones.
3. "Learning" means searching for good values of the weights. Gradient descent does the searching — measure how wrong the current weights are and follow the slope downhill — and the chain rule (backpropagation) is what makes computing that slope cheap, even for millions of weights.

Seen this way, machine learning is a different way to program a computer: instead of writing the function yourself, you write its *signature* (an architecture with millions of tunable parameters), define what "good output" looks like (a loss function), and let an optimization algorithm fill in the implementation.

## The model: from a matrix to an MLP

Back to MNIST — an MNIST image is 28×28 pixels. Flatten it and you get a vector $x$ of 784 numbers between 0 (white) and 1 (black). We want a function that maps that vector to an answer: which digit is this?

<FlattenFigure />

Notice that the problem itself isn't deterministic. A sloppily written 5 shades into a 2; even humans disagree about the worst examples. So a function that returns *the* answer is the wrong shape — what we want is a function that weighs the evidence and returns a *score* for each of the 10 candidates, which we can treat as (and will shortly convert into) probabilities. Again, we're doing statistics, not logic.

The simplest mechanism in all of statistics for turning many weighted pieces of evidence into a score is a regression — a linear function of the input:

$$
\tip{10 scores — one per digit}{y} = \tip{a 10×784 matrix of learned weights}{W}\tip{the image as a vector of 784 pixel values}{x} + \tip{10 learned offsets — one per digit}{b}
$$

where $W$ is a 10×784 matrix of weights and $b$ is a vector of 10 biases. Each row of $W$ is effectively a template: the dot product between the input and that row measures "how much does this image look like this row's digit." This alone — a *linear classifier* — gets about 92% accuracy on MNIST, which tells you something important: a matrix multiply is already a primitive form of pattern matching.

<LinearScoresFigure />

Why does a linear model top out at 92%? Because of what linearity *means*: each pixel gets one fixed weight, votes independently, and the votes are simply added up. A linear model cannot express "this pixel is evidence for an 8 — but only if this *other* region is dark too." The pixels of a 5 and a 2 overlap heavily; what distinguishes them is the *combination* of strokes, and combinations are exactly what a weighted sum can't see. In programming terms: a linear function is a program with no `if` statements — one pass of weighted arithmetic, no decisions that depend on the input.

You might try to fix this by stacking two linear layers. But composing linear functions just gives you another linear function ($W_2(W_1x) = (W_2W_1)x$ — the composition collapses into one matrix). However many layers you stack, you've written a longer program with still no `if` statements.

The fix is to insert a nonlinearity between the layers, and the field has settled on the almost comically simple [ReLU](https://en.wikipedia.org/wiki/Rectifier_%28neural_networks%29): $\mathrm{relu}(x) = \max(0, x)$. Look at what it does: below zero the unit outputs nothing; above zero it passes its signal through. That's a branch — the smallest possible `if`. With a nonlinearity between them, the layers stop collapsing: the first layer can compute features, the ReLU can *decide* which ones are present, and the second layer can weigh combinations of those decisions.

Stack linear layers with nonlinearities between them and you have a **multi-layer perceptron** (MLP):

$$
y = \tip{second layer: weighs combinations of features into digit scores}{W_2} \, \tip{the branch: zeroes out features that aren't present}{\mathrm{relu}}(\tip{first layer: detects 512 features in the pixels}{W_1 x + b_1}) + b_2
$$

With one hidden layer of 512 units, this gets ~98% on MNIST. Intuitively, the first layer learns to detect features (strokes, loops, corners), and the second layer learns to combine features into digits.

<MlpFigure />

But stacking the layers broke something important. A lone regression can be *solved*: for a linear model, calculus hands you the best-fit weights directly — set the derivative of the error to zero and solve the equations (this is least squares, the same machinery that fits a trend line in a spreadsheet). The moment a nonlinearity sits between two matrices, that machinery dies. For a linear model the error surface is a smooth bowl — "set the derivative to zero" is a system of *linear* equations with one solution. Add the ReLUs and the surface shatters into an exponential number of pieces, and "set the derivative to zero" becomes a system of nonlinear equations nobody can solve in general. This isn't just empirical pessimism: [Blum and Rivest proved](https://people.csail.mit.edu/rivest/pubs/BR93.pdf) that optimally training even a three-neuron network is NP-complete, so a general-purpose recipe for the best $W_1$ and $W_2$ would, among other things, resolve P vs. NP. The best anyone knows how to do is start with random weights and improve them *iteratively* — which is exactly what the rest of this chapter is about.

## The learning: gradient descent

So here's where we are: an MLP with ~400,000 weights, every one of them initialized to a random number. Feed it our 7 and it reports something like 10% on every digit — of course it does; it's random. How do we get 400,000 random numbers to take on *useful* values?

Since we can't solve for them, we iterate: nudge the weights, check whether the model got better, keep the nudges that help, repeat a few hundred thousand times. For now, assume that "did the model get better?" is a single number we can compute — a score, called the **loss** $L$, that measures how wrong the model is on the training data, where lower is better. (Constructing it carefully is the next section's job; here we only need that it exists and is smooth.)

Here's the situation for any single weight. Somewhere out there is its *optimal* value — the setting that makes the model least wrong. We don't know how to find it; that's the closed-form door that slammed shut a section ago. What we *do* know how to compute, for whatever value we currently have, is how bad it is (the loss) — and, because the loss is smooth, which direction makes it worse (the derivative). That suggests a humble strategy: repeatedly move in whichever direction makes things less bad, and stop when no direction helps. You may never learn where the best value was, but you'll settle somewhere *least bad*.

<GradientDescentFigure />

Scaled up to all 400,000 weights at once, this is **gradient descent**: compute the gradient of the loss — the direction that increases it fastest — and take a small step the other way.

$$
\tip{a weight}{\theta} \leftarrow \theta - \tip{the learning rate: how big a step to take}{\eta} \tip{the slope: how much the loss changes as this weight changes}{\frac{\partial L}{\partial \theta}}
$$

This update runs for every weight simultaneously. Each weight's partial derivative, collected into one big vector, is the **gradient** — papers write the whole update as $\theta \leftarrow \theta - \eta \nabla_\theta L$, and now you can read that too.

Why a *small* step — and why must the steps shrink as we close in? Imagine taking the same confident stride every time: nearing the valley floor, you'd overshoot it, land on the opposite slope, turn around, and overshoot again — orbiting the minimum forever without ever landing on it. Gradient descent has an elegant built-in fix: the step is $\eta$ *times the slope*, and the slope fades to zero at the minimum, so the steps shrink automatically as you arrive — exactly what the animation above shows. Here's the fixed-stride version for comparison:

<FixedStepFigure />

The multiplier $\eta$ is the **learning rate**, and it is the single most finicky number in all of deep learning. Too small is merely slow — thousands of timid steps down a hill you could have descended in ten. Too large is fatal, and it's worth seeing exactly why, because it seems to contradict the self-shrinking steps we just celebrated. That guarantee had a hidden assumption: that each step lands you *closer* to the minimum, where the slope is gentler and the next step therefore smaller. Overshoot far enough, though, and you land on the far slope at a point *steeper* than the one you left. Now "step proportional to slope" works against you: a steeper landing means a bigger next step, which means a steeper landing still. The same feedback loop that damped the walk now amplifies it, and the parameters ricochet outward until the numbers overflow. On our parabola you can make this exact: each step multiplies your distance from the minimum by a fixed factor set by $\eta$ — below the threshold that factor is less than one and the walk converges; above it, every step pushes you further away than you started.

Two practical modifications matter:

- **Stochastic** gradient descent: you *could* compute the exact gradient over all 60,000 images before each step — but consider what that buys you. The gradient from a random sample of images is an unbiased estimate of the full gradient, and its accuracy improves only with the square root of the sample size, while its cost grows linearly. Worse, extra precision is mostly thrown away: you only take one small step in that direction, and after the step the landscape has changed and the direction must be recomputed anyway. So instead, estimate the gradient on a random **batch** (say, 128 images) per step: for the price of one perfect step you take ~500 noisy ones, and 500 stumbles downhill travel much farther than one flawless stride. (The noise even turns out to *help* — it jiggles the trajectory out of flat regions and bad ruts.)
- **Epochs**: one full pass through the training data is an epoch. Small datasets get looped over many times. (Foreshadowing: LLMs, trained on trillions of tokens, typically see their data roughly *once* — more on that in Chapter 7.)

## The loss: measuring wrongness

Now let's construct the number we've been assuming. Gradient descent quietly imposed two requirements on it: the loss must be *differentiable* (we take its gradient), and it should change *continuously* as the model improves (a compass that only moves in rare jumps gives the search no direction). Defining it well matters as much as the architecture does — it is, literally, the spec the model will be optimized against.

Those requirements immediately disqualify the obvious candidate: accuracy, percent correct. Nudge one weight slightly and usually *no* prediction flips, so accuracy doesn't move at all — flat almost everywhere, gradient zero, no signal. What we want instead is a number that rewards moving from "99% sure it's a 3" to "60% sure it's a 3" on an image of a 5, even though both are, discretely, the same mistake. That means grading the model's *confidence*, not just its verdict — and for that, its outputs need to be probabilities.

The 10 output scores (called **logits**) are unbounded real numbers. To interpret them as a probability distribution, we pass them through **softmax**:

$$
\tip{the probability assigned to digit i}{p_i} = \frac{\tip{exponentiate: always positive and amplifies gaps}{e^{y_i}}}{\tip{normalize: divide by the total so everything sums to 1}{\sum_j e^{y_j}}}
$$

Softmax exponentiates each score (making everything positive, and amplifying differences) and normalizes so they sum to 1. Here it is applied to the scores our linear classifier produced for the 7:

<SoftmaxFigure />

The target it's graded against is the label written as a **one-hot** vector — all zeros except a 1 on the correct digit: a probability distribution with all of its mass on the truth. The grading rule is **cross-entropy loss**: the negative log of the probability the model assigned to the correct answer.

$$
\tip{the loss — what gradient descent minimizes}{L} = \tip{negated so that more confidence means less loss}{-\log}(\tip{the probability the model gave the right answer}{p_{\text{correct}}})
$$

The log of a probability has a name you'll meet in every LLM API: a **logprob**. Probabilities live in [0, 1], so logprobs live in [−∞, 0] — zero when the model is certain, increasingly negative as it's surprised — and cross-entropy is just the correct answer's logprob, negated. If the model puts probability 1 on the right answer, the loss is 0. If it puts probability 0.01 on it, the loss is ~4.6.

<details>
<summary>Why the log, rather than something simpler like penalizing $1 - p_{\text{correct}}$?</summary>

One statistical reason and one practical one. Statistically, the natural goal is to maximize the probability of getting the *whole training set* right — and since that's a product of 60,000 per-example probabilities, it's hopeless to work with directly (it would underflow any floating-point format, and calculus hates products). Taking the log turns the product into a *sum* of per-example terms — exactly our loss — without changing what's being maximized.

Practically, the log changes how wrongness is punished: a linear penalty barely distinguishes "wrong at 1%" from "wrong at 0.001%", so the gradient fades just when correction is most needed. Under the log, every additional order of magnitude of overconfident wrongness costs the same again — the loss stays fierce precisely where the model is most confidently wrong.

(There's a third, deeper reading — the logprob is the number of bits needed to encode the right answer under the model's beliefs — that pays off next chapter, when training a language model turns out to be compression.)

</details>

Averaged over the dataset, this single number summarizes how wrong the model is — smooth, differentiable, and falling steadily as confidence shifts toward the right answers. "Learn to read digits" has become "minimize this function."

## Backpropagation: the chain rule, industrialized

How do you compute a gradient with respect to a million parameters? First, a term: running the network front-to-back — pixels in, through the layers, predictions out — is called a **forward pass**; it's what the model does every time it makes a prediction (during training, we then score those predictions against the label to get the loss). Now, the naive way to get the gradient: nudge one parameter, run a forward pass, and see how the loss moved. That works — it's literally the definition of a derivative — but it costs one forward pass *per parameter*: a million forward passes to take a single step.

[Backpropagation](https://karpathy.medium.com/yes-you-should-understand-backprop-e2f06eab496b) computes *all* of the gradients in about the cost of two forward passes. It's the chain rule from multivariate calculus, applied with dynamic programming: run the network forward, remember the intermediate values, then walk backward from the loss, multiplying local derivatives as you go. The gradient of the loss with respect to any weight is the product of the derivatives along the path from that weight to the loss.

<BackpropFigure />

The chain above had one path, but a real network is a *graph* — and this is where backprop's dynamic programming pays off. Here's a full two-input network; follow any weight's gradient back from the loss:

<ComputationalGraphFigure />

Every formula begins with the same factors. Backprop computes $\partial L/\partial \hat{y}$ once, each $\partial L/\partial h$ once, and every weight upstream reuses them — which is how a million gradients cost about the same as two forward passes instead of a million.

In practice you never write this by hand. Frameworks like PyTorch record the **computational graph** as your code runs and derive the backward pass automatically (this is "autograd"). Here is the entire training loop, for real:

```python showLineNumbers
model = nn.Sequential(
    nn.Linear(784, 512),
    nn.ReLU(),
    nn.Linear(512, 10),
)
opt = torch.optim.SGD(model.parameters(), lr=0.1)

for images, labels in dataloader:          # batches of 128
    logits = model(images.view(-1, 784))   # forward pass
    loss = F.cross_entropy(logits, labels) # softmax + neg-log-likelihood
    opt.zero_grad()
    loss.backward()                        # backprop: fills in .grad
    opt.step()                             # gradient descent step
```

Every model in this book — up to and including the frontier ones — is trained by a scaled-up version of these ten lines.

## Better optimizers: momentum and Adam

Vanilla SGD works, but the loss landscape of a real network is a mess of ravines and plateaus, and two refinements are so universal you should know them by name.

**Momentum** keeps a running average of recent gradients and steps in that direction — like a ball rolling downhill, it smooths over noise and powers through small bumps.

**[Adam](https://arxiv.org/abs/1412.6980)** additionally tracks a running average of the gradient's *magnitude* for each individual parameter, and scales each parameter's step size accordingly: parameters with consistently large gradients get smaller steps, and vice versa. It's a per-parameter adaptive learning rate. The variant actually used everywhere is [AdamW](https://arxiv.org/abs/1711.05101), which fixes how weight decay (a regularization term) interacts with the adaptivity.

When you read an LLM paper and see "AdamW, β₁ = 0.9, β₂ = 0.95," those betas are just the decay rates of the two running averages. One consequence worth filing away for the infrastructure chapters: Adam stores two extra numbers *per parameter*, so the optimizer's state is twice the size of the model itself.

## What training actually looks like

On paper, training is "run the loop until the loss is low." In practice, training is *staring at the loss curve* — and knowing what to check, in what order, when it isn't doing what you want. For our MNIST net, the ritual looks like this:

**First number: the loss at initialization.** Before any training, a 10-class model with random weights should assign roughly 10% to everything, so its cross-entropy should be almost exactly $-\ln(1/10) \approx 2.3$. Check it. If it's 7, your initialization is broken; if it's 0.3, you have a bug (probably your data is leaking the answer). This one free sanity check catches a remarkable fraction of setup errors before you've spent a single GPU-minute.

**First milestone: overfit one batch.** Take 32 images and train on just those until the loss is ~0. A network that can't *memorize* 32 examples has a plumbing problem — wrong shapes, a broken loss, gradients not flowing. This proves the machinery works before you ask it to learn anything real. Skipping this step is the classic way to spend a day debugging the wrong layer of the stack.

**Then: watch the shape.** With the plumbing verified, start real training and read the curve. There are only three shapes, and the learning rate usually picks between them:

<LossCurvesFigure />

When the curve diverges, lower the learning rate; when it crawls, raise it. The standard move is a sweep over powers of ten — nobody, at any level of seniority, guesses it correctly on the first try. For our MNIST MLP, a healthy run takes the loss from 2.3 to under 0.1 within a couple of epochs, and accuracy to ~98%.

**What matters, in order.** For a fixed dataset, the learning rate dwarfs everything else; after that, training longer and making the model bigger; after *that*, the architecture tweaks people love to argue about. And looming over all of it: more and better data beats all of the above — a hierarchy so reliable it becomes the thesis of Chapter 4. Karpathy's [A Recipe for Training Neural Networks](https://karpathy.github.io/2019/04/25/recipe/) is the canonical write-up of this discipline, and it transfers almost unchanged from MNIST to frontier models.

There's one curve we haven't mentioned yet, though — and it's the one that actually matters.

## Generalization: the point of all this

One last concept, because it's the difference between machine learning and curve fitting. A model with enough parameters can *memorize* its training set — and score 100% on it while being useless on new data. This is **overfitting**, and it's why we always hold out a **test set** the model never trains on, and report accuracy there. In practice you watch *two* loss curves during training — one on training data, one on held-out data — and the number you actually care about is the second. When the training curve keeps falling but the held-out curve turns back upward, the model has stopped learning and started memorizing.

The entire game is generalization: we don't want a model that knows these 60,000 digits, we want one that has learned what digits *are*. Keep this tension in mind — it returns with a vengeance when we discuss benchmark contamination in Chapter 9.
