# Neural networks: Functions that learn

<ByLine />

In 1989, researchers at Bell Labs built a system to read handwritten ZIP codes off envelopes. The dataset they eventually assembled — 70,000 grayscale images of handwritten digits, called [MNIST](https://en.wikipedia.org/wiki/MNIST_database) — became the "hello world" of machine learning, and it's where we'll start too.

## Programming with data

Programming a computer to read these scribbles is brutally hard with classical logic. There are no hard-and-fast rules for what makes a 5 a 5 — every rule you write has a thousand exceptions — and the early vision systems built on hand-written rules fell on their faces. The same wall appears wherever the input is fuzzy: parsing an English sentence, recognizing a face in a photo. This is why these problems stayed unsolved for decades while computers conquered chess. But problems like these have a saving grace: the rules are hard to write, but *examples* are cheap — and the discipline for extracting patterns from examples is statistics.

That's the thread this chapter pulls on, in three steps:

1. We treat digit-reading as a statistics problem. The simplest statistical tool is a regression — give every pixel a weight, add up the evidence — and this alone reads 92% of digits correctly.
2. But a regression is linear: it can weigh each pixel, but it can't see *combinations* of strokes. Stacking regressions with small decisions between them — a neural network — lets us learn arbitrary functions, not just linear ones.
3. "Learning" means searching for good values of the weights. Gradient descent does the searching — measure how wrong the current weights are and follow the slope downhill — and the chain rule (backpropagation) is what makes computing that slope cheap, even for millions of weights.

Seen this way, machine learning is a different way to program a computer: instead of writing the function yourself, you write its *signature* (an architecture with millions of tunable parameters), define what "good output" looks like (a loss function), and let an optimization algorithm fill in the implementation.

## The model: from a matrix to an MLP

Back to MNIST — an MNIST image is 28×28 pixels. Flatten it and you get a vector $x$ of 784 numbers between 0 (white) and 1 (black). We want a function that maps that vector to an answer: which digit is this?

<FlattenFigure />

Notice that the problem itself isn't deterministic. A sloppily written 5 shades into a 2; even humans disagree about the worst examples. So a function that returns *the* answer is the wrong shape — what we want is a function that weighs the evidence and returns a *score* for each of the 10 candidates, which we can treat as (and will shortly convert into) probabilities. Again, we're doing statistics, not logic.

The simplest mechanism in all of statistics for turning many weighted pieces of evidence into a score is a regression — a linear function of the input:

$$
y = Wx + b
$$

where $W$ is a 10×784 matrix of weights and $b$ is a vector of 10 biases. Each row of $W$ is effectively a template: the dot product between the input and that row measures "how much does this image look like this row's digit." This alone — a *linear classifier* — gets about 92% accuracy on MNIST, which tells you something important: a matrix multiply is already a primitive form of pattern matching.

<LinearScoresFigure />

Why does a linear model top out at 92%? Because of what linearity *means*: each pixel gets one fixed weight, votes independently, and the votes are simply added up. A linear model cannot express "this pixel is evidence for an 8 — but only if this *other* region is dark too." The pixels of a 5 and a 2 overlap heavily; what distinguishes them is the *combination* of strokes, and combinations are exactly what a weighted sum can't see. In programming terms: a linear function is a program with no `if` statements — one pass of weighted arithmetic, no decisions that depend on the input.

You might try to fix this by stacking two linear layers. But composing linear functions just gives you another linear function ($W_2(W_1x) = (W_2W_1)x$ — the composition collapses into one matrix). However many layers you stack, you've written a longer program with still no `if` statements.

The fix is to insert a nonlinearity between the layers, and the field has settled on the almost comically simple [ReLU](https://en.wikipedia.org/wiki/Rectifier_%28neural_networks%29): $\mathrm{relu}(x) = \max(0, x)$. Look at what it does: below zero the unit outputs nothing; above zero it passes its signal through. That's a branch — the smallest possible `if`. With a nonlinearity between them, the layers stop collapsing: the first layer can compute features, the ReLU can *decide* which ones are present, and the second layer can weigh combinations of those decisions.

Stack linear layers with nonlinearities between them and you have a **multi-layer perceptron** (MLP):

$$
y = W_2 \, \mathrm{relu}(W_1 x + b_1) + b_2
$$

With one hidden layer of 512 units, this gets ~98% on MNIST. Intuitively, the first layer learns to detect features (strokes, loops, corners), and the second layer learns to combine features into digits.

<MlpFigure />

But stacking the layers broke something important. A lone regression can be *solved*: for a linear model, calculus hands you the best-fit weights directly — set the derivative of the error to zero and solve the equations (this is least squares, the same machinery that fits a trend line in a spreadsheet). The moment a nonlinearity sits between two matrices, that machinery dies. For a linear model the error surface is a smooth bowl — "set the derivative to zero" is a system of *linear* equations with one solution. Add the ReLUs and the surface shatters into an exponential number of pieces, and "set the derivative to zero" becomes a system of nonlinear equations nobody can solve in general. This isn't just empirical pessimism: [Blum and Rivest proved](https://people.csail.mit.edu/rivest/pubs/BR93.pdf) that optimally training even a three-neuron network is NP-complete, so a general-purpose recipe for the best $W_1$ and $W_2$ would, among other things, resolve P vs. NP. The best anyone knows how to do is start with random weights and improve them *iteratively* — which is exactly what the rest of this chapter is about.

## The loss: measuring wrongness

So here's where we are: an MLP with ~400,000 weights, every one of them initialized to a random number. Feed it our 7 and it reports something like 10% on every digit — of course it does; it's random. How do we get 400,000 random numbers to take on *useful* values?

Since we can't solve for them, we iterate: nudge the weights, check whether the model got better, keep the nudges that help, repeat a few hundred thousand times. For that loop to work at all, "did the model get better?" has to be a number we can compute — a single score that any candidate set of weights can be graded by, so the search can tell whether a change helped or hurt. That number is the **loss**, and defining it well matters as much as the architecture does — it is, literally, the spec the model will be optimized against.

The obvious candidate — accuracy, percent correct — turns out to be a terrible compass. Nudge one weight slightly and usually *no* prediction flips, so accuracy doesn't move at all: the search gets no signal about which direction is better. What we want instead is a number that improves *continuously* as the model gets less wrong — one that rewards moving from "99% sure it's a 3" to "60% sure it's a 3" on an image of a 5, even though both are, discretely, the same mistake. That means grading the model's *confidence*, not just its verdict — and for that, its outputs need to be probabilities.

The 10 output scores (called **logits**) are unbounded real numbers. To interpret them as a probability distribution, we pass them through **softmax**:

$$
p_i = \frac{e^{y_i}}{\sum_j e^{y_j}}
$$

Softmax exponentiates each score (making everything positive, and amplifying differences) and normalizes so they sum to 1. Here it is applied to the scores our linear classifier produced for the 7:

<SoftmaxFigure />

Then we score the prediction with **cross-entropy loss**: the negative log of the probability the model assigned to the correct answer.

$$
L = -\log(p_{\text{correct}})
$$

If the model puts probability 1 on the right answer, the loss is 0. If it puts probability 0.01 on it, the loss is ~4.6. Averaged over the dataset, this single number summarizes how wrong the model is — and turns "learn to read digits" into "minimize this function."

This exact loss — softmax over possible outputs, negative log-likelihood of the correct one — is also *the* loss used to train LLMs. The only thing that changes is that the 10 digits become ~100,000 tokens.

## The learning: gradient descent

So we have a function with hundreds of thousands of parameters and a loss we want to minimize. The search algorithm is almost embarrassingly greedy: compute the gradient of the loss with respect to every parameter — the direction that increases the loss fastest — and take a small step the other way.

$$
\theta \leftarrow \theta - \eta \nabla_\theta L
$$

The step size $\eta$ is the **learning rate**, and it is the single most finicky number in all of deep learning: too small and training takes forever, too large and the parameters ricochet around and diverge.

<GradientDescentFigure />

Two practical modifications matter:

- **Stochastic** gradient descent: you *could* compute the exact gradient over all 60,000 images before each step — but consider what that buys you. The gradient from a random sample of images is an unbiased estimate of the full gradient, and its accuracy improves only with the square root of the sample size, while its cost grows linearly. Worse, extra precision is mostly thrown away: you only take one small step in that direction, and after the step the landscape has changed and the direction must be recomputed anyway. So instead, estimate the gradient on a random **batch** (say, 128 images) per step: for the price of one perfect step you take ~500 noisy ones, and 500 stumbles downhill travel much farther than one flawless stride. (The noise even turns out to *help* — it jiggles the trajectory out of flat regions and bad ruts.)
- **Epochs**: one full pass through the training data is an epoch. Small datasets get looped over many times. (Foreshadowing: LLMs, trained on trillions of tokens, typically see their data roughly *once* — more on that in Chapter 7.)

## Backpropagation: the chain rule, industrialized

How do you compute a gradient with respect to a million parameters? You could nudge each parameter, re-run the model, and see how the loss changes — but that requires a million forward passes per step.

[Backpropagation](https://karpathy.medium.com/yes-you-should-understand-backprop-e2f06eab496b) computes *all* of the gradients in about the cost of two forward passes. It's the chain rule from multivariate calculus, applied with dynamic programming: run the network forward, remember the intermediate values, then walk backward from the loss, multiplying local derivatives as you go. The gradient of the loss with respect to any weight is the product of the derivatives along the path from that weight to the loss.

In practice you never write this by hand. Frameworks like PyTorch record the **computational graph** as your code runs and derive the backward pass automatically (this is "autograd"). Here is the entire training loop, for real:

```python
model = nn.Sequential(
    nn.Linear(784, 512),
    nn.ReLU(),
    nn.Linear(512, 10),
)
opt = torch.optim.SGD(model.parameters(), lr=0.1)

for images, labels in dataloader:          # batches of 128
    logits = model(images.view(-1, 784))   # forward pass
    loss = F.cross_entropy(logits, labels) # softmax + neg-log-likelihood
    opt.zero_grad()
    loss.backward()                        # backprop: fills in .grad
    opt.step()                             # gradient descent step
```

Every model in this book — up to and including the frontier ones — is trained by a scaled-up version of these ten lines.

## Better optimizers: momentum and Adam

Vanilla SGD works, but the loss landscape of a real network is a mess of ravines and plateaus, and two refinements are so universal you should know them by name.

**Momentum** keeps a running average of recent gradients and steps in that direction — like a ball rolling downhill, it smooths over noise and powers through small bumps.

**[Adam](https://arxiv.org/abs/1412.6980)** additionally tracks a running average of the gradient's *magnitude* for each individual parameter, and scales each parameter's step size accordingly: parameters with consistently large gradients get smaller steps, and vice versa. It's a per-parameter adaptive learning rate. The variant actually used everywhere is [AdamW](https://arxiv.org/abs/1711.05101), which fixes how weight decay (a regularization term) interacts with the adaptivity.

When you read an LLM paper and see "AdamW, β₁ = 0.9, β₂ = 0.95," those betas are just the decay rates of the two running averages. One consequence worth filing away for the infrastructure chapters: Adam stores two extra numbers *per parameter*, so the optimizer's state is twice the size of the model itself.

## Generalization: the point of all this

One last concept, because it's the difference between machine learning and curve fitting. A model with enough parameters can *memorize* its training set — and score 100% on it while being useless on new data. This is **overfitting**, and it's why we always hold out a **test set** the model never trains on, and report accuracy there.

The entire game is generalization: we don't want a model that knows these 60,000 digits, we want one that has learned what digits *are*. Keep this tension in mind — it returns with a vengeance when we discuss benchmark contamination in Chapter 9.
