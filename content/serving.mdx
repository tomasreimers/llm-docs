# Serving: Making it fast and cheap

<Byline readingTime={metadata.readingTime} />


Between "we trained a great model" and "an API that serves a planet" sits some of the best systems engineering of our time — and it's a shame how little of it most engineers see, because it's the part of the stack built from ideas you already know: virtual memory, batch schedulers, caches, compression. This chapter reverse-engineers the price-per-million-tokens on the invoice.

The physics from last chapter, restated as the serving problem: decode is memory-bound — the GPU reads ~all active weights to emit each token, using ~1% of its compute. Every technique below is one of three moves, and they're the chapter's arc:

1. **Share the bytes** — batch many conversations onto each read of the weights (continuous batching), and stop wasting the memory that limits the batch (PagedAttention, prefix caching).
2. **Shrink the bytes** — quantization, and at the limit, distillation: shrink the model itself.
3. **Read the bytes less often** — speculative decoding: multiple tokens per weight-read.

## Continuous batching: share the bytes

The waste in serving one user is that 140 GB of weights get read to produce *one* token. Serve 100 conversations in a single batch, and the same read produces 100 tokens — per-token cost falls ~100× before any cleverness. Throughput providers live and die on batch size (and this is why per-token API prices can sit so far below what a dedicated GPU would cost you).

Before the scheduling trick, pin down the plumbing — *where does a generated token actually go?* Both places, in different forms. The decode loop is **GPU-resident**: the weights, every conversation's KV cache, and the step itself all live in HBM, and the newly sampled token never leaves — it's appended on-GPU as the next step's input, and its K/V join the cache. What crosses back over PCIe each step is just the sampled token *ID* — a few bytes per live request — which the **CPU-side engine** detokenizes, streams to the user, checks against stop conditions, and feeds to its scheduler. The GPU does the arithmetic; the CPU runs the airport:

The wrinkle is that requests don't arrive in lockstep: one user's answer is 10 tokens, another's is 3,000. Naive batching waits for the longest member to finish — like an elevator that won't open until every rider's floor is reached. **Continuous batching** (also "in-flight batching") schedules at the granularity of a *single token step*: finished requests exit the batch and queued ones enter, immediately. It's a job scheduler where the quantum is one forward pass, and it's table stakes in every serving engine:

<ContinuousBatchingFigure />

The tradeoff it navigates is the classic one — **throughput vs. latency**. Bigger batches amortize better but make everyone wait a bit longer per token. The two numbers on every serving dashboard: **TTFT** (time to first token) and **tokens/sec** thereafter. TTFT is queueing plus **prefill** — Chapter 10's name for processing the whole prompt, which must finish before the first output token can exist (all input tokens in parallel, so compute-bound and fast — but a 100K-token prompt is still real work). Tokens/sec thereafter is **decode**, the memory-bound crawl this chapter is about. Batch APIs at half price are this tradeoff sold explicitly: your overnight jobs are the ballast that fills the batches.

## PagedAttention: stop wasting the memory

Batching's limiter is memory: every concurrent conversation carries its KV cache (Chapter 5), and the caches compete with the weights for HBM. Early servers allocated each request a *contiguous* max-length buffer, and here is why that's catastrophic. A response's length is unknown when it starts, so a contiguous allocation must reserve for the worst case: a request that will turn out to emit 50 tokens books a 4,096-token slab up front, and the unwritten tail sits idle for the request's entire life — **internal fragmentation**. Meanwhile, requests finish at unpredictable times, punching holes of unpredictable sizes into memory — and because the next arrival needs its slab *contiguous*, free memory accumulates in gaps individually too small to use even when they sum to plenty — **external fragmentation**. The vLLM team measured production servers holding actual KV entries in as little as **20–40%** of the memory nominally "used" for caches: a museum-quality reproduction of pre-virtual-memory operating systems.

The fix, from the [vLLM paper](https://arxiv.org/abs/2309.06180), is called **PagedAttention** and it is exactly what its name promises: chop KV caches into fixed-size blocks (~16 tokens), allocate on demand from a shared pool, and translate through a per-request block table. Virtual memory, reinvented for attention — fragmentation vanishes, effective batch size jumps, and — just as page tables enabled shared memory — two requests with the same prefix can *map the same physical blocks*.

One clarification the name invites: the GPU does **not** reach back into system RAM — "paging" here borrows the bookkeeping, not the disk. The entire block pool is carved out of HBM at startup (whatever's left once the weights move in); the "page table" is just a small array of block indices per request; and the attention kernel is written to gather each block through that one extra indirection — pointer-chasing the GPU does itself, inside HBM, at full bandwidth. The CPU-side scheduler (the anatomy figure above) updates the tables as it allocates and frees, but the hot path never crosses PCIe, and there is no page fault: a request that can't get a block simply waits. (The analogy does extend one level further, deliberately: under real memory pressure, vLLM can *swap* a preempted request's blocks out to CPU RAM — or drop them and recompute later. That's an eviction tier for the queue, never the serving path.)

That last trick matters more than it sounds, because real traffic is wildly prefix-heavy: every request from your app shares the same long system prompt; every turn of a chat shares all previous turns; every step of an agent loop (next chapter) re-sends a growing transcript. **Prefix caching** — keeping hot prefixes' KV blocks resident and skipping their prefill entirely — is why providers bill "cached input tokens" at a steep discount, and why you should structure prompts with the stable parts first (a genuinely actionable takeaway: put the variable parts of your prompt at the *end*).

At the frontier, serving splits further: **prefill/decode disaggregation** runs the compute-bound prefill and memory-bound decode on *separate GPU pools*, so neither workload's utilization profile poisons the other's.

## Quantization: shrink the bytes

If decode speed is bytes-of-weights ÷ bandwidth, then halving the bytes doubles the ceiling. **Quantization** stores numbers in fewer bits — 16-bit floats down to 8-bit or 4-bit integers — by mapping each weight group's range onto a small grid (plus per-group scale factors, and care for outlier values, which is where methods like [GPTQ](https://arxiv.org/abs/2210.17323) and [AWQ](https://arxiv.org/abs/2306.00978) earn their citations).

The empirical miracle: weights at 8-bit cost essentially nothing in quality, and 4-bit costs remarkably little — the giant undertrained matrices simply don't need the precision (that a 70B model works at 4 bits/weight is itself a clue about how diffusely information is stored — Chapter 6 again). The knee just below 4 bits is no accident of one codebase — [Dettmers & Zettlemoyer](https://arxiv.org/abs/2212.09720) measured the tradeoff across model families and scales and found 4-bit sitting at the optimum: for a fixed memory budget, a *bigger model at 4 bits beats a smaller one at 8*, and below 4 bits the quality cost finally outruns the size savings. A 70B model at 4 bits is ~35 GB: one GPU instead of two, double the decode ceiling, or a frontier-class model on a MacBook — the entire local-LLM scene is downstream of this one technique. Quantizing the *KV cache* pays the same dividend to context length. And there's a third thing to quantize: the **activations** — Chapter 1's term for the values flowing *through* the network during a forward pass, as opposed to the stored weights and cache. That target matters for a different reason: weight-only quantization helps the memory-bound decode (fewer bytes to move), but prefill is *compute*-bound, and the arithmetic only gets cheaper if *both* operands of each multiply shrink — quantize the activations too (fp8) and the tensor cores themselves run at roughly double rate. The costs of all of it are workload-dependent and show up in the tails, so the eval discipline of Chapter 9 applies to your quantized deployment as much as to any model swap.

## Speculative decoding: read the bytes less often

The most conceptually delightful trick, from [Leviathan et al.](https://arxiv.org/abs/2211.17192) (and [Chen et al.](https://arxiv.org/abs/2302.01318)): most tokens are *easy* — finishing "the United States of" doesn't need a trillion parameters. But decoding makes the big model pay full price for every token.

So: let a small, fast **draft model** race ahead and propose several tokens, then have the big model check them *all in one forward pass*.

Why is checking cheap when generating isn't? Recall why decode is serial in the first place: token *n+1* can't be computed until token *n* exists, because token *n* is its input. But once the draft has *written down* four candidate tokens, that dependency is gone — the sequence is just text now, and the big model can process existing text the way it processes a prompt or a training batch (Chapter 3's causal-mask trick): every position at once, one read of the weights. That single pass hands back the big model's next-token prediction at *every* position — what it would have said after the context, after the context plus the first draft token, after the first two, and so on — and verification is nothing more than comparing those predictions against the draft's proposals. The draft model has converted a *generation* problem (serial, one weight-read per token) into a *reading* problem (parallel, one weight-read total), and Chapter 10 taught us those live on opposite sides of the roofline:

<SpeculativeFigure />

Accept the longest agreeing prefix; where the draft went wrong, the big model's own prediction takes over. A careful accept/reject rule makes the output distribution **provably identical** to the big model's — this is a lossless speedup, pure latency win, typically 2–3×. When the models agree, you've paid one weight-read for several tokens: arithmetic intensity, raised again.

Variants abound, in two directions worth naming. **Self-drafting** removes the second model: Medusa-style setups bolt extra prediction heads onto the big model itself — head *k* learns to predict the token *k* steps ahead, so one forward pass proposes its own candidates. And **n-gram lookahead** (prompt lookup) needs no model at all: draft by string-matching against text already in the context — free, and shockingly effective for editing and coding, where the output quotes the input at length.

Then there's the radical version of the same instinct — the promised diffusion cameo, which deserves a real paragraph. **Diffusion models**, the architecture behind the image generators, work by iterative refinement: start from pure noise and sculpt it toward a sample over a few dozen denoising steps. **Diffusion language models** ([LLaDA](https://arxiv.org/abs/2502.09992) is the open demonstration) port this to text: start with a block of, say, 1,000 masked tokens, and at each step let the model fill in and *revise every position in parallel*, conditioned on the whole current draft — closer to BERT's cloze objective (Chapter 3's other lineage) than to GPT's next-token game, run repeatedly until the block settles. The serving arithmetic is the attraction: an autoregressive model reads its weights 1,000 times to emit 1,000 tokens; a diffusion model reads them once per refinement pass — a few dozen times *total* — and every pass is a big, parallel, prefill-shaped operation on the compute-bound side of Chapter 10's roofline. [Gemini Diffusion](https://deepmind.google/models/gemini-diffusion/) demos low-thousands of tokens per second on exactly this math. The open questions are just as real: quality at frontier scale is unproven; each refinement re-reads the *whole block*, so the KV cache's append-only economics don't transfer; and text, unlike pixels, is consumed left-to-right — by readers streaming an answer and by agents acting mid-generation. The honest summary: a bet on breaking the one-token-at-a-time bottleneck entirely rather than speculating past it. Watch that space; don't reorganize around it.

## Distillation: shrink the model itself

The endgame move is older than everything above ([Hinton et al., 2015](https://arxiv.org/abs/1503.02531)). **Distillation**: use a big **teacher** model to train a small **student** — and mechanically, it's Chapter 1's training loop with one substitution. Ordinary training grades the student against a one-hot target: *the next token is "mat"; every alternative is equally, maximally wrong.* Distillation grades it against the **teacher's entire output distribution** at that position — mat 60%, sofa 25%, rug 10%, carburetor ~0 — with a loss that asks the student's distribution to match the teacher's (the same KL divergence that leashed RLHF in Chapter 8, now promoted from guardrail to objective). Hinton called what this transfers *dark knowledge*: the teacher's carefully ranked wrong answers encode how concepts relate, so every single token delivers a vocabulary-wide training signal instead of one bit of right/wrong — which is why a student can reach a quality its size could never have reached from raw text alone.

In practice the commonest form is cruder, because you usually can't get a teacher's distributions (APIs return sampled tokens, not logits): generate millions of teacher transcripts and run SFT on them — Chapter 8's recipe with the teacher as the annotator — distilling through samples rather than soft targets. The mini/flash/lite tier of every model family is some blend of distillation and Chapter 4's over-training; R1's distilled small models are how reasoning reached laptops within *weeks* of its release.

Distillation is why "capability lag" keeps shrinking: whatever the frontier does expensively this quarter, a distilled model does cheaply next quarter. It's also, notoriously, how competitors bootstrap from each other's APIs — every lab's terms of service forbid it, and every lab is suspected of it.

None of these techniques knows anything about language. It's caches, pages, schedulers, and compression — your field, aimed at one workload. The invoice line "per million tokens" is the price of bytes moved through HBM, divided by how cleverly they're shared.

And after all of it — the pools, the pages, the drafts — notice what the serving stack actually delivers: not text. A probability distribution, fresh from the softmax, a hundred thousand candidates wide, every few milliseconds. Someone still has to decide what to *do* with it — and that deciding turns out to be the last mile where products are won: the difference between a model that completes your sentence and one that writes valid JSON, calls your APIs, and runs for an hour unsupervised. One chapter left, and it's the one you'll use most.
